# Spec: Queue CLI

**Created:** 2026-08-28
**Version:** v0.1
**Status:** In Progress -- v0.1 -- 34/? questions resolved
**Iteration:** 1

## Summary

A centralized `queue` CLI that replaces the 3 independent hook/webhook systems that exist today (task-cli CLI-only hooks, flow-cli CLI+HTTP hooks, web-backend internal EventBus). Producers push named events with a JSON payload; subscribers are configured per-project. The producer decides whether the dispatch is fire-and-forget (`onXxx`) or blocking (`beforeXxx`, waits for all subscriber responses with structured return). Supersedes the unresolved `meta-hooks-flow-cli` spec and formally replaces decision D32 ("hook failures silently ignored").

## Decision Log

| #                | Decision                                                                                                                                                                                                                                                                                      | Status   | Date       | Rationale                                                                                                                                           |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-1              | `onXxx` = async (fire-and-forget), `beforeXxx` = blocking (waits for subscriber response)                                                                                                                                                                                                     | Resolved | 2026-08-28 | P-1 + industry convention (Fastify, NestJS); producer decides blocking via event name prefix                                                        |
| D-2              | `beforeXxx` return contract: `{action: 'continue', payload?: {...}}` or `{action: 'abort', reason: string}`                                                                                                                                                                                   | Resolved | 2026-08-28 | `reason` required on abort so the producer (e.g. flow-cli) can surface a meaningful error                                                           |
| D-3              | meta-hooks-flow-cli spec (2026-08-17, 0/6 questions resolved) is superseded by this spec                                                                                                                                                                                                      | Resolved | 2026-08-28 | queue CLI covers the same problem space (D32, ordering, richer payloads) with a broader scope                                                       |
| D-4              | Queue -> Orchestrator direction is out of scope                                                                                                                                                                                                                                               | Resolved | 2026-08-28 | Orchestrator (@wadeck/orchestrator) is a cron scheduler; on-demand triggers go directly to the command, no benefit in routing via queue             |
| D-5              | Orchestrator -> Queue: orchestrator natively emits `onJobStart`, `onJobCompleted`, `onJobFailed` to queue                                                                                                                                                                                     | Resolved | 2026-08-28 | 3 native queue push calls in scheduler.ts after exit code capture; no `&&` hacks                                                                    |
| D-6              | Delivery guarantee: WAL (write before dispatch) + exponential backoff retry + dead letter queue after X failures; `beforeXxx` = immediate error if subscriber unavailable, no retry                                                                                                           | Resolved | 2026-08-28 | `beforeXxx` is synchronous -- retrying a blocking gate makes no sense. `onXxx` needs guaranteed delivery for pipeline chains (Cluster 2)            |
| D-7              | Queue is a short-lived daemon: starts on first `queue push`, auto-shuts down after 1 minute of inactivity                                                                                                                                                                                     | Resolved | 2026-08-28 | No always-on process wasting resources; pushes are bursts not continuous flow; consistent with singleton-daemon-kit pattern                         |
| D-8              | Retry scheduling delegated to orch: on failed `onXxx` dispatch, queue registers a one-shot job in orch (`orch add --once --delay <backoff> "queue retry --event <id>"`). Orch handles _when_, queue handles _what_.                                                                           | Resolved | 2026-08-28 | Clean separation of concerns; orch is already a long-lived daemon designed for scheduling                                                           |
| D-9              | Mutual pre-condition check: queue verifies orch is available before scheduling retries; orch verifies queue is available before emitting events. Hard error with actionable message if not found -- no silent fallback.                                                                       | Resolved | 2026-08-28 | P-2 (no silent failure); global principle: "no silence, explicit error with actionable info"                                                        |
| D-10             | Subscriber config: global `~/.config/queue/subscribers.yml` + project `.queue/subscribers.yml`, merged at dispatch time (project overrides global for same event)                                                                                                                             | Resolved | 2026-08-28 | Scope per project required; consistent with task-cli/flow-cli pattern (superseded by D-34 for merge strategy -- APPEND, not override)               |
| D-11             | Payload filtering: two syntaxes supported -- simplified dot-notation `meta.projectName=agent-fleet` and full JSONPath `$.meta.projectName == "agent-fleet"`. Both filter matches AND misses must be logged.                                                                                   | Resolved | 2026-08-28 | Dot-notation covers 80% of cases with zero learning curve; JSONPath for complex expressions; logging misses required to debug misconfigured filters |
| D-12             | Event name wildcards supported in subscriber config: `ticket.*` (single segment), `ticket.>` or `ticket.**` (any depth). Matched at dispatch time before payload filtering.                                                                                                                   | Resolved | 2026-08-28 | Covers "subscribe to all ticket events" without listing each one; consistent with NATS/RabbitMQ topic routing                                       |
| D-13             | `beforeXxx` multiple subscribers: sequential waterfall in declaration order. Each subscriber receives the `payload` field from the previous response (not the wrapper). First `{action: 'abort'}` stops the chain; remaining subscribers not called. (see D-27 for payload forwarding detail) | Resolved | 2026-08-28 | Waterfall required because payload can be enriched/modified by each subscriber. In practice 0-1 subscribers, so sequential latency is negligible.   |
| D-14             | CLI subscriber payload transport: stdin only (JSON). `beforeXxx` subscriber reads stdin, writes modified payload to stdout (JSON). No env vars. No command string interpolation of payload fields -- payload is ONLY available via stdin (prevents command injection, see D-28).              | Resolved | 2026-08-28 | Clean Unix contract; preserves nested structures and arrays faithfully; no dual mechanism to maintain                                               |
| D-15             | DLQ: retry count + backoff configurable per subscriber (default: 5 retries, exponential backoff). DLQ stored in `~/.config/queue/dlq.ndjson` with full context. Commands: `queue dlq list`, `queue dlq replay --id`, `queue dlq clear`. (see D-29 for maxDlqSize)                             | Resolved | 2026-08-28 | Per-subscriber config needed: pipeline events (10 retries) vs notifications (2 retries) have different criticality                                  |
| D-16             | Standard event envelope: every event is wrapped as `{id, timestamp, event, payload, meta: {cwd, projectName?}}`. `meta` is auto-populated by `queue push` from cwd. Enables `meta.projectName=agent-fleet` filters (D-11).                                                                    | Resolved | 2026-08-28 | Consistent envelope enables cross-event filtering without requiring producers to manually add context                                               |
| D-17             | HTTP subscriber options: `url`, `method` (default POST), `headers` (map), `timeout` (default 10s). Payload sent as JSON body. `beforeXxx` HTTP: response body must be `{action, payload?, reason?}`.                                                                                          | Resolved | 2026-08-28 | Mirrors HookDispatcher HTTP support; timeout default from existing convention                                                                       |
| D-18             | Package name: `@wadeck/queue-cli`. Distribution: same pattern as flow-cli/task-cli (Go launcher, esbuild bundle, platform packages, `~/.config/queue/` config dir, `@wadeck/shared-cli` for ConfigDir + UpdateManager).                                                                       | Resolved | 2026-08-28 | Consistent with cli-distribution spec and cli-status-and-next decisions                                                                             |
| D-19             | CLI commands: `queue push <event> <json> [--timeout <duration>]`, `queue status`, `queue list-subscribers [event]`, `queue dlq list/replay/clear`, `queue retry --event <id>`, `queue start/stop/status` (daemon), `queue logs [--follow]`.                                                   | Resolved | 2026-08-28 | Minimal surface covering all identified use cases                                                                                                   |
| D-20             | No migration needed: HookDispatcher configs are not in active production use. queue CLI replaces from scratch with no backward-compat shim.                                                                                                                                                   | Resolved | 2026-08-28 | Nothing is running currently; migration tooling would be dead code                                                                                  |
| D-21             | `onXxx` multiple subscribers: dispatched in parallel. Each subscriber has its own independent WAL entry and retry state.                                                                                                                                                                      | Resolved | 2026-08-28 | No dependency between async subscribers; parallel maximizes throughput; each failure is isolated                                                    |
| D-22             | `beforeXxx` timeout: default 30s, overridable by producer (`queue push --timeout 60s`). Timeout = abort with reason `"subscriber timeout after Xs"`. Subscriber has no say -- if non-critical, use `onXxx` instead.                                                                           | Resolved | 2026-08-28 | P-1: producer controls semantics. D-1: beforeXxx = gate by design; a non-critical subscriber belongs on onXxx.                                      |
| D-23             | All WAL writes go through the daemon exclusively -- producers never write WAL directly. Prevents concurrent-write corruption.                                                                                                                                                                 | Resolved | 2026-08-28 | A-02: two simultaneous queue push processes could corrupt NDJSON WAL without this constraint                                                        |
| D-24             | `beforeXxx` stdout contract: empty stdout = pass-through (continue with original payload); invalid JSON on stdout = abort with reason "subscriber returned invalid JSON".                                                                                                                     | Resolved | 2026-08-28 | A-01: undefined behavior on empty/invalid stdout would silently corrupt or pass gating                                                              |
| D-25             | Self-healing retry chain: each queue retry call re-registers the next backoff attempt with orch before dispatching. Daemon startup scans WAL for unscheduled pending entries and re-registers them. Daemon shutdown scans WAL for pending entries and schedules them before exiting.          | Resolved | 2026-08-28 | A-03/CON-01/CON-05: without self-healing, a pending event can get stuck forever if orch was down at scheduling time                                 |
| D-26             | meta field is flat: `meta.projectName` (not `meta.project.name`). D-11 filter examples use `meta.projectName=agent-fleet`.                                                                                                                                                                    | Resolved | 2026-08-28 | CON-02: D-16 and D-11 were inconsistent on field naming                                                                                             |
| D-27             | `beforeXxx` waterfall payload forwarding: each subscriber receives the `payload` field from `{action: 'continue', payload}`, not the wrapper. First subscriber receives the original event payload.                                                                                           | Resolved | 2026-08-28 | CON-03: ambiguous whether wrapper or inner payload was forwarded                                                                                    |
| D-28             | Security constraint: no command string interpolation of payload fields. Payload is ONLY available via stdin. This prevents command injection.                                                                                                                                                 | Resolved | 2026-08-28 | S-02: explicit constraint needed even though stdin-only already prevents it                                                                         |
| D-29             | DLQ maxDlqSize: default 1000 entries per subscriber. Oldest entries pruned with warn log when exceeded.                                                                                                                                                                                       | Resolved | 2026-08-28 | S-06: unbounded DLQ growth on permanently-down subscriber                                                                                           |
| D-30             | WAL, DLQ, and log files created with owner-only permissions (600 on Unix; user-only ACL on Windows).                                                                                                                                                                                          | Resolved | 2026-08-28 | S-03: payloads may contain sensitive data                                                                                                           |
| D-31             | Filter-miss logs include full envelope `{id, timestamp, event, meta}` but MAY omit payload body for brevity.                                                                                                                                                                                  | Resolved | 2026-08-28 | S-05: filter-miss trace needed for debugging misconfigured filters                                                                                  |
| D-32-replacement | Legacy systems removal: task-cli HookDispatcher, flow-cli HookDispatcher, and web-backend EventBus external dispatch are explicitly removed upon queue CLI integration. No coexistence.                                                                                                       | Resolved | 2026-08-28 | CON-04: P-3 requires replacement not addition; removal must be explicit                                                                             |
| D-33             | `@wadeck/orchestrator` must add `--once --delay <duration>` support (one-shot delayed job) before queue CLI retry scheduling (D-8) can be implemented. This is a pre-requisite.                                                                                                               | Resolved | 2026-08-28 | Feature required for D-8; orch is the designated scheduler per our design discussion                                                                |
| D-34             | Global + project merge for same event = APPEND: both sets of subscribers fire. Project subscribers do not replace global subscribers.                                                                                                                                                         | Resolved | 2026-08-28 | Natural use case: global monitoring subscriber + project-specific action subscriber on same event                                                   |
