## Decisions

| #   | Subject                                                   | Decision                                                                           | Why                                                                                                                                                                                                                                                                                                                                                                                        |
| --- | --------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | Workspace + approval built-ins (7 manifests)              | **Kept as is** (manifest system). Not migrated.                                    | The registry contract (`FlowPlugin`) needs `create` returning an instance with `dispose`; `WorkspaceProvider`/`ApprovalProvider` have none, and no owner calls one. Registry-first via `PluginProviderLoader` also flips today's precedence: an explicit `pluginsDir` currently wins over a built-in (`PluginLoader.ts:227`), the bridge ignores it with a warning. That is a user-visible change to `plugins.workspace` / `plugins.approval` `pluginsDir`. Manifests are also still needed by `flow plugins` and the flow-core catalog parity test, so a migration would keep both. Not a "same behaviour" move, so out of scope for a simple first version. |
| 2   | `PluginProviderLoader`                                    | **Kept, not deleted**, flagged dead in production.                                 | Referenced by `PluginProviderLoader.test.ts` and documented as the migration bridge. Deleting it is the alternative if the migration is abandoned.                                                                                                                                                                                                                                         |
| 3   | `plugin-none`                                             | **Kept**, deletion candidate.                                                      | Referenced by `PluginLoader.test.ts` (22), `ConfigLoader.test.ts`, `PluginResolver.test.ts`, `CliSmoke.integration.test.ts`, `PluginRoutes.test.ts`, catalog tests, `PLUGINS.md`, `flow-cli/package.json`. Only the deprecated `plugins.workspace` section reaches it. Remove together with that section.                                                                                    |
| 4   | Fork                                                      | **Daemon path unchanged**; plugin comment rewritten; equality test added.          | The plugin's `create` and the daemon both build through the single factory `buildForkWorkerType`, so there is one implementation. Routing the daemon through `create` would make a synchronous startup step async and add a failure path for no gain. `ForkWorkerTypePlugin.test.ts` ("builds the same worker as the daemon path") asserts identical spawn arguments and environment. |
| 5   | T-02-load gate                                            | Guard test + threat-model row (**OPEN-gate**).                                     | `packages/flow-cli/src/config/PluginLoadGate.test.ts` scans `packages/*/src` production files and fails when one outside `ALLOWED_PRODUCTION_FILES` uses `PluginModuleLoader` or `loadPlugin`; the message says what the threat note must answer (source of the path/package, who can write it, what code runs with which rights). Also fails on a stale allowlist entry. Row added to `.claude/threat-model.md`. |

## Not done

- No built-in manifest was migrated to the registry; no config key, error text or load precedence changed.
- Nothing was deleted.
- The scan covers `packages/*/src`; build scripts (`packages/*/ci`) and non-TS loaders (`import()` written by hand) are outside it. A hand-written dynamic `import()` of a config value is not detected.

## How to reopen

- Migrating the 7 built-ins needs, first: (a) a decision on `pluginsDir` precedence for built-ins (keep user override, or accept the registry-first rule and document the break); (b) `dispose` on `WorkspaceProvider`/`ApprovalProvider` with an owner that calls it, or a lighter registry contract without it; (c) manifests kept for `flow plugins`, or the catalog derived from the registry. Then wire `PluginProviderLoader` in `PluginResolver` and `WorkspaceProviders` (about 6 files plus tests).
- Wiring a config-supplied path/package into `loadPlugin`: write the T-02-load note in `.claude/threat-model.md` first, then add the file to `ALLOWED_PRODUCTION_FILES`.
- Fork through the registry: only if a second host needs `host.fork`; make `createDaemonForkWorkers` async and call `forkWorkerTypePlugin.create`.
