# flow-sandbox

Shared sandbox layer over Docker Sandboxes (`sbx`). Private, not published, no dependency on queue packages. Plan: `.claude/plans/2026-10-25_docker-sandbox-worker.md` (milestone M1).

## Classes

| Class                             | Role                                                                                                                      |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `SandboxRuntime` (interface)      | create, exec (stdin/env/cwd/streaming/abort), stop, start, remove, list, copy, per-sandbox network rules and secrets      |
| `SbxCliRuntime`                   | the only class that builds `sbx` command lines; also implements `SbxIntrospection` (version, diagnose, policy, settings)  |
| `FakeSandboxRuntime`, `FakeClock` | in-memory runtime for later milestones: records calls, injects failures, idle stop simulated                              |
| `SbxPrerequisiteCheck`            | tool, pinned version, daemon, sign-in, policy initialized; reports network mode and ssh agent forwarding; changes nothing |
| `PathTranslator`                  | `C:\x` <-> `/c/x`, everything must stay inside the two mounts; warns on Windows paths in env or script text               |
| `SandboxOptionsParser`            | strict options (unknown key = error)                                                                                      |

Rules enforced by `SbxCliRuntime`: `shell:false`, hidden window, `MSYS_NO_PATHCONV=1`, explicit `--cpus`/`-m`, `--sandbox` on every rule and secret (no API for a global one), env through a private `--env-file`, secrets read by sbx from a command, version must equal `PINNED_SBX_VERSION` (`src/PinnedSbxVersion.ts`).

sbx location: `binaryPath` option, `SBX_MOCK_PATH`, `SBX_PATH`, `%LOCALAPPDATA%\DockerSandboxes\bin\sbx.exe`, then PATH. A configured but missing path is an error.

## Tests

`npm run test --workspace=flow-sandbox`. Tests run `SbxCliRuntime` against `src/testing/sbx-mock.mjs` through real child processes (state and call log in `SBX_MOCK_STATE_DIR`, failures via `SBX_MOCK_SCENARIO`). `FakeSandboxRuntime` and `SbxCliRuntime` share `testing/SandboxRuntimeContract.ts`.

Needs `bash` on PATH (Git for Windows on Windows): `CredentialProcessScript.test.ts` and `CredentialGlueInstaller.test.ts` run the real bash scripts. Without it they fail in `beforeAll` (`testing/BashRequirement.ts`) with that message; they never skip. No test needs the real `sbx`, AWS, Docker or the network beyond loopback; `src/exec/McpInjectionInvariant.test.ts` stages the image's `mcp-server.cjs` itself, so no build step comes before the tests.

## Mock fidelity

Real captures (sbx 0.51.0, `fixtures/sbx-0.51.0/`, written by `scripts/CaptureSbxFixtures.mjs`: read-only commands, plus one throw-away `flow-sbx-capture-*` sandbox with one scoped rule so `ls-json` and `policy-ls-json` are populated; it refuses to write them empty): version, `ls --json`, `diagnose --json`, `policy ls --json`, `settings ls --json`, `--help` of the verbs used, "sandbox not found" errors. The mock validates flags against the captured help and `SbxMockFidelity.test.ts` compares its output with the captures.

SYNTHETIC (invented by the mock, verified only by the live check):

- failure outputs of not signed in, policy not initialized, daemon down, unhealthy daemon (a failing `diagnose` check status is assumed to be anything but `pass`)
- success text of create/stop/rm/cp/exec, "already exists" error, `policy allow/rm`, `secret set-custom/rm`
- shape of a user-added per-sandbox policy rule; `secret rm --placeholder` (appears in the help examples but not in its Flags list)
- the `deny-all` policy shape (assumed: no global network allow rule)

No drift check in `scripts/check-mock-drift.js`: it probes a CLI in PATH against a cache written by a real-CLI suite, and sbx is neither. Instead `SbxMockFidelity.test.ts` fails when the fixtures are not from `PINNED_SBX_VERSION`. Real-binary drift is checked by hand: re-run the capture and review `git diff fixtures`.

## Live check (gated, never in CI)

`SBX_LIVE=1 node --import tsx packages/flow-sandbox/scripts/live/SbxLiveCheck.mjs` creates one `flow-sbx-live-*` sandbox, runs the PoC commands (2 mounts, env + stdin exec, streaming, abort vs stop, restart, copy, scoped allow, scoped secret), and removes everything. It refuses without `SBX_LIVE=1` and when `SBX_MOCK_PATH` is set. `SBX_LIVE_DRY_RUN=1` runs it against the mock to test the script only (bash steps fail there by design).

## Limits

- `PathTranslator` is lexical; symlinks and junctions are rejected by `RunMounts` (M3).
- `start` is an `exec true` (sbx has no start verb).
- Windows ignores the file mode `0600` of the secret and env files (`PrivateSecretFile`, `PrivateEnvFile`, the wrapper secrets directory): on Windows they are as private as the temp directory of the account (the default `%TEMP%` was measured readable by the account, SYSTEM, the administrators and, inherited, a local group on this machine). The secret and env files and the secrets directory of a wrapper now get an owner-only ACL on Windows (`PrivateAcl`: inheritance removed, full control for the current user by SID, applied before anything is written; a failure stops the write, no silent fallback; verified with the real tool in `PrivateAcl.test.ts` and by a full real run in which sbx still reads the secret). Residual: a wrapper does not check that `%TEMP%` itself is private; do not point `TEMP` at a shared folder. A wrapper killed hard leaves its `flow-sbx-<exec|harness>-secrets-<wrapperId>-*` and `flow-sandbox-env-*` directories behind; at startup `StaleTempSweep` removes those older than 24 h whose wrapper is not running (env directories only while no wrapper runs), logging each removal.
- Host abort of `exec` does not stop the process in the VM; call `stop`.

Project-directory warning (`RunMounts`): the workspace equals the `projectDir` option, or `<workspace>/.git` is a directory (regular checkout; worktrees and submodules have a `.git` file). A `.git` file warns that git does not work in the VM.

Limits: `endRun('daemon_stopping')` stops without removing and does not mark the run ended (a later step restarts the sandbox); execution ids that are not lowercase `[a-z0-9-]` are refused (flow's real id format is unchecked); a recycled pid makes a dead wrapper look alive (removal refused); `remove` checks liveness then acts (no lock); `scripts/` is outside the eslint config.

### Restart of a stopped sandbox (measured, sbx 0.51.0, one machine, 2026-11-13)

`PluginLiveCheck` (`idleStopMinutes=0.2`) runs: a VM step, a `host: true` step that sleeps 24 s (the wrapper stops the idle VM after 12 s), a VM step, a model step. Two runs gave the same picture.

| What                        | Measured                                                                                                                                                                                                                                                                                               |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Who restarts it             | the wrapper, at the next step (`SandboxLifecycle.restart`, an `exec true`); `sbx ls` read `running`, `stopped`, `running`                                                                                                                                                                              |
| Time                        | create 5.7 to 5.8 s to be ready (first step), restart 2.1 to 2.2 s (second run: 2089 and 2168 ms; `toSandboxReadyMs` of the wrapper timing line); the whole step 2.6 s                                                                                                                                 |
| The VM                      | it is rebooted: `boot_id` changes, uptime restarts at about 2 s. Processes of the VM are gone                                                                                                                                                                                                          |
| Files                       | the files the VM wrote on its own disk (`/tmp`, `$HOME`) are still there; the mounts are in place (workspace file written before the gap read back, workspace and `.meta` writable); the hostname and the proxy variables are unchanged                                                                |
| Credentials, rules, secrets | still in place: the model step after the restart answered (credential endpoint, network rules and secret work); while stopped `sbx policy ls` still lists the sandbox's rules (1 to 2 lines) and `sbx secret ls` its secret (0 to 1 line: the count varied between the two runs and I do not know why) |
| Leak                        | none found: at the end of the run the sandbox, its rules and its secret are gone (`sbx ls`, `policy ls`, `secret ls`); the script copies staged in `/tmp/flow-staged` are removed at the end of each process (the one file seen is the running step's own)                                             |

**A restart happens only within a run.** The sandbox name is `flow-sbx-<wrapperId>-<executionId>` (`SandboxLifecycle.beginStep`, `SandboxLifecycle.ts:127`), so another run never has the name of an earlier one, and each run's first assignment creates a fresh sandbox. A restart is the idle stop followed by the next step of the SAME run (`restart`, same file). The files the VM keeps in `/tmp` and `$HOME` survive that restart (measured above) and go away only with the sandbox, which `endRun` removes at the end of the run; `run-ended` refuses a late step of a finished run (`SandboxLifecycle.ts:130`), so the removed sandbox is not created again. No case carries VM files from one run to another:

- a new run on a wrapper that holds a stopped sandbox of an earlier run creates its own sandbox; the old one is not restarted and not removed (decision 26: only `leftover remove` removes it; `reapOwn` at wrapper start only STOPS own running leftovers, `LeftoverSandboxes.ts:84`);
- a leftover sandbox of the SAME execution (a resumed run after a wrapper restart) is not reused either: `createFor` finds the name taken and the step is refused with `already-exists`, naming `leftover remove <name>` (`FailedCreateCleanup.ts:53`), so a resume needs the leftover removed first and then starts on a fresh sandbox, with the workspace and `.meta` (not the VM's disk) carrying what the run wrote.
  Pinned by `SandboxLifecycle.test.ts`, "no sandbox is reused across runs" (a VM file seeded in run 1 is absent in run 2; the stopped leftover is neither restarted nor removed; the same-execution leftover is refused).

What this does NOT show: a restart after sbx's own idle stop (the check uses the wrapper's), a restart under heavy host load, or the behaviour on another host. Files an agent leaves on the VM's disk survive a stop: nothing here removes them before the next step, only the removal at the end of the run does.

## M4: development harness (relay variant, not a product)

A standalone wrapper that a `built-in:command` worker source starts. It registers with the daemon as one worker, runs each assigned step inside a sandbox with the real flow worker bundle, and relays the messages. No core change: routing is by label (`--labels sandbox` on the source, `labels: [sandbox]` in the flow).

Run: declare the source once (full example in the header of `scripts/HarnessWrapper.mjs`), give the steps `labels: [sandbox]`, `flow run`. Options are strict: a bad or missing one prints the usage. Logs: the wrapper writes to stderr (the daemon prints it as `[source <id>] ...`) and to `--log-file`. Live acceptance: `SBX_LIVE=1 node --import tsx packages/flow-sandbox/scripts/live/HarnessLiveCheck.mjs` (about 1.5 min, 13 assertions, isolated daemon, one real sandbox and one real Bedrock call, everything it created is removed). By default a never-served last step (`parked`) keeps the run, and so the daemon, alive so that the wrapper's own idle timer can be watched; `HARNESS_PARK=0` lets the flow itself complete (the daemon then stops about a second later and the sandbox is stopped through `daemon_stopping`).

### G1: the bridge token through the sbx proxy (measured, sbx 0.49.2, `scripts/live/BridgeTokenProbe.mjs`)

| Channel of the WebSocket connection    | Proxy substitutes the placeholder                               |
| -------------------------------------- | --------------------------------------------------------------- |
| request header (`x-flow-bridge-token`) | yes, exact value, also with two custom secrets for `localhost`  |
| `Sec-WebSocket-Protocol`               | yes (the connection then fails: the server selects no protocol) |
| query string                           | no                                                              |
| first WebSocket message                | no (frames are opaque after the upgrade)                        |

The harness uses the header. It only works for clients that go through the proxy:

- The VM sets `HTTP(S)_PROXY` and `NODE_USE_ENV_PROXY=1`. Node's built-in `WebSocket`/`fetch` and `curl` use the proxy; the `ws` library and raw sockets do NOT, and then the bridge sees the placeholder text (401). The shim therefore uses the built-in `WebSocket`.
- The flow worker starts a model CLI with an isolated environment (PATH, HOME, step env): the proxy variables are dropped, so `credential_process` (curl) went direct and the endpoint saw the placeholder ("unknown bearer secret"). `VmProxyEnvironment` copies the VM's proxy variables into the model env and fails loudly when the VM has none.
- What the token is for: only the process the wrapper started can open the bridge, not another process of the host. It is NOT a barrier against code in the same VM: the placeholder is in the environment of the shim, readable by any process of the user `agent` (the live check proves a second connection is refused with 409, not that the token is secret from the VM).

### Observations about sbx (one machine, Windows 10, one run each; report to the sbx/threat-model owners)

- Raw TCP (sbx 0.51.0, `scripts/live/RawTcpLiveCheck.mjs`, 2026-11-08, one machine). Observed on the HOST side: with no rule, none of three host servers (127.0.0.1, 0.0.0.0, the LAN address; reached via `host.docker.internal` or by address) saw a connection from the VM; with `sbx policy allow network --sandbox <name> localhost:<port>` a raw `/dev/tcp` client reached exactly that port (banner received) and no other host port. Observed only inside the VM, with no receiving side: the handshake completes with ANY address, even an unroutable one (`192.0.2.1:443`), so a completed handshake proves nothing, and `1.1.1.1:443` gave a TLS EOF. Nothing is established about public destinations. The earlier note here (0.49.2, M4: a raw client reached a ruleless host port and the internet by IP) most likely counted completed handshakes; it was not re-run on 0.49.2.
- Workspace lifetime: the removed `mode: isolated` workspace was deleted at the end of the run, so a stopped sandbox could not restart (`422 workspace directory ... no longer exists`). A pool slot is never deleted by flow; restarting a stopped sandbox on a pool slot was not re-measured on real sbx (only the mock covers it).
- The real plugin end to end (`scripts/live/PluginLiveCheck.mjs`, sbx 0.51.0, real Bedrock, pool workspace, 2026-11-08): the bound run completed (script step in the VM, model step answered); `sbx rm --force` took 577 ms at the end of the run; the pool claim was released 758 ms AFTER the end of `sbx rm`, i.e. the daemon released the workspace only after the removal (claim polled every 20 ms). First run of the plugin on the real sbx: the image preflight failed because `sbx template ls` prints `docker.io/library/flow-sandbox` where the matcher expected `flow-sandbox`; fixed (`SbxTemplateListing`).

### Mounts: links and read-only (sbx 0.51.0, 2026-11-08; `SymlinkLiveCheck.mjs`, `ReadOnlyLiveCheck.mjs`)

- Symbolic links cannot be created on a mount from inside the VM, as the agent user or as root (`Permission denied`; hard links: `Invalid cross-device link`). A junction made on the host appears in the VM as a symlink with a relative target and does not resolve outside the mounts. `RunMounts` still rejects links: it protects against links already in the workspace (a pool slot, a project) and against other sbx versions.
- A `:ro` secondary mount is enforced by the HOST side (virtiofs), not only by VM mount options. As root, after `remount,rw`, `remount,bind,rw` (mountinfo then shows the mount `rw`), a bind in a new mount namespace, a second `mount -t virtiofs -o rw host` of the whole share, a bind of that, and `mount(2)` called from python, every write still returned `Read-only file system` and the host file stayed unchanged. The same second mount can write the read/write workspace and shows only the mounted paths' ancestors; a new file next to the mounts got `Permission denied`.
- Not tested: virtiofs protocol-level attacks, kernel exploits, other channels of the VM. The primary (first) mount must be read/write.

### Workspaces a sandboxed worker accepts

Only `workspace: pool`, declared as `workspaces: ['pool']` in the manifest and on the instance (kept equal by a test). The core checks it when the run starts, before any allocation: a flow that requires the sandbox with another kind is refused with `WORKSPACE_KIND_NOT_ACCEPTED` (no run, no sandbox, no slot; `SandboxPluginE2e`). The kind is the built-in name used in the flow: the inline form `workspace: { provider: pool, dir: ..., count: ... }` is the kind `pool`. A configured NAMED provider instance (`plugins.instances.<name>`) cannot be listed in a manifest, so a source that restricts its kinds never accepts a flow that names one. `SandboxableWorkspace` below stays as defence in depth, because the kind is coarse.

Only `workspace: pool`. `in-place` and `readonly` hand the sandbox the project folder, including `<project>/.flow` (flow definitions, outputs of other runs) and `.git/hooks`; `worktree` has a `.git` file whose gitdir is outside the mounts. The wrapper refuses them (`SandboxableWorkspace`): the run's `.meta` (from `executionContext.outputsDir`) must lie outside the workspace after resolving links and junctions, which also refuses a pool slot that contains the project.

With the server answered while git runs (asynchronous spawn), control = a fetch with nothing planted: no helper ran. Planted in `.git/config`, the helper RAN on a plain `git fetch`, on `git ls-remote` and on `hardenedGit` mutating `fetch`: `credential.helper = !sh script` ran (`get`, and `erase` after the failure), the url-scoped `credential.<url>.helper` ran, and `core.askPass` ran when it was an executable (git spawns the value as a program, not through a shell: a script without the exec bit fails with "cannot spawn"; the POSIX form with the exec bit was not run here). A `hardenedGit` reading call (`status`) contacts no remote and ran nothing, so `GitFolderProbe` is not exposed. `hardenedGit` does not neutralise any of these on a mutating fetch or clone, which matches its own "not covered" note; a fix has a cost (an empty `credential.helper=` also removes the user's own helper), so it is a decision for the core.

So the daemon's reads are safe from fsmonitor, hooks and filter drivers; mutating calls (the flow's sync step, your own tools) are not. Use dedicated slots, re-clone them, or restore `.git/config`, `hooks/`, `info/` and `.gitattributes` in the sync step before any mutating git call. Not covered: the legacy web-backend git service, FlowWorker git calls, the user's own tools. The user's global git config is out of reach of the sandbox: only the ancestors of the mounts are visible in the host user directory, and nothing could be created there as agent or root (this machine, one run).

### Leftover sandboxes: explicit command (decision 26)

Never automatic. A wrapper only reports leftovers at start and stops (never removes) its own sandboxes on exit. List and remove with the command the artifact ships, no source checkout needed: `node <plugins-dir>/plugin-sandbox/wrapper.cjs leftover list` and `... leftover remove <name> [--force]` (the repository script `scripts/LeftoverCli.mjs` is the same code). `remove` takes one exact name, refuses a name without the plugin's `flow-sbx-` marker and a sandbox whose run or wrapper is alive (presence files), and `--force` only overrides a missing presence directory. Covered by `SandboxPluginArtifact.test.ts` (list, refusal, removal, usage error).

### Limits of the harness

- One run per wrapper lifetime (no run-end events: the relay harness does not declare `run-events`; the exec variant does): a step of another run fails with `worker-busy`. The sandbox is left STOPPED, never removed (`LeftoverCli.mjs list|remove`). When the daemon goes away the run is interrupted with `daemon_stopping` (stop and keep).
- No reconnect to the daemon (the launch token is one-shot).
- The registered sandbox worker also takes steps WITHOUT labels (routing prefers registered workers; flow-owner finding H4). Do not register it on a daemon whose other flows you do not want in the VM.
- The daemon asks its sources again whenever a step finds no free worker, without a cap on launches: 5 launches of the wrapper for one 4-step run were observed, 4 refused by the wrapper-id lock (`presence`). It also forks a local worker 3 s after asking if none arrived.
- `inject_steps` is relayed from a started model step without re-validating the steps (the daemon validates; to be checked in M6). Secrets are sent into the VM in the `assign` (accepted residual T-02).
- `HarnessMain` (wiring) and `InnerBridgeMain` (VM entry) have no unit test; the live check covers them.
- Windows host paths in step env or script text are logged as warnings, not translated.

### Plugin `sandbox.exec` (the way to declare the sandbox worker)

**Status (2026-11-13).** Run for real, on one machine (Windows 10, sbx 0.51.0, real Bedrock): `PluginLiveCheck` passed 15 of 15 on the real sbx in the run flow-owner did on the user's machine (second attempt: the first failed on an image preflight, see the image option) and in ours; it has since grown (18 of 19 in our last full run, the 19th being the Codex step, which needs its own profile and runs separately: 5 of 5), with a real flow daemon in an isolated directory, the built plugin and real sandboxes. It covers a VM script, a `host: true` script, a model step, implicit confinement, `profile: inspect` (read-only workspace), a pool behind a link, the restart of a stopped sandbox, and a Codex and an OpenCode step (the last two in separate runs: each needs a profile that may call its models). The mock end-to-end test (`SandboxPluginE2e`, in `npm test`) covers the same routing without a VM. Measured numbers: see "Restart of a stopped sandbox" and "Mounts". NOT shown: any POSIX host (macOS, Linux) outside the unit tests, another sbx version, a daemon under load, and everything listed as "not proven" in the sections below.

Build the artifact from the checkout (it is not published, there is no CI step for it):

```
npm run bundle --workspace flow-sandbox
```

It writes `packages/flow-sandbox/dist-plugin/` (ignored by git): `plugin-sandbox/plugin.config.js` (about 17 KB, plain JS, read by the daemon), `plugin-sandbox/wrapper.cjs` (about 920 KB: the exec wrapper with the engine and the sandbox layer, started with node) and `plugin-sandbox/mcp-server.cjs` (flow's MCP server; the engine looks for it next to the wrapper). Rebuild after changing flow-cli: the wrapper embeds its engine.

Declare the source once (the plugin ref `sandbox.exec` makes the source declare the sandbox guarantees; `--provider` is only a label; `<id>` is any source id, for example `sandbox-1`):

```
flow worker source add sandbox-1 --provider sandbox --plugin sandbox.exec \
  --plugins-dir <absolute path of packages/flow-sandbox/dist-plugin> \
  --option projects=<project ids> --option region=us-east-1 --option profiles=claude=<aws profile> \
  --option image=flow-sandbox:m7 --option pull=never
```

Then restart the daemon (a plugin is loaded once per daemon) and write the flow with `requires: [sandbox]` at flow level (see "Routing and isolation" and "Requiring guarantees" below: this is what keeps injected steps in the sandbox, and without it the wrapper refuses the step). The daemon builds the source at its first contact with it.

| Option (flat string, `--option key=value`)                    | Required | Meaning                                                                                                                                                                                                                          |
| ------------------------------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `projects`                                                    | yes      | project registry ids, comma separated (`flow project list`); the daemon hands a plugin source no projects. The manifest declares these names (`options`, taken from the parser table, kept equal by a test), so `flow worker source add` refuses a misspelt `--option` (`project=a` gives `Did you mean "projects"`, exit 1) before it is stored; a stored unknown name warns in `flow worker source list` and the daemon log. Options are parsed strictly and nothing is ignored: an unknown name, an empty value, an empty list item, a duplicate project, a profile entry without `alias=profile`, a value the format cannot express (a profile name with a comma) each fail when the source is built, with a message that names the option and gives an example. One thing cannot be detected by the plugin: the same `--option key` given twice (flow's CLI keeps the last one before the plugin sees the options). A credential must never be an option (flow refuses sensitive keys unless written `${ENV_VAR}`, which the daemon expands from its own environment; the AWS credentials come from your AWS profile through the host credential endpoint, not from options).

The daemon mints one launch credential per ask (at most 32 outstanding per source). An ask that starts nothing because a wrapper of the source is already alive returns `{ launched: false }`, which gives that credential back (the contract of `WorkerObtainResult` in `extension-points`); an ask that starts a wrapper returns `{ launched: true }` and keeps it.

What happens when the daemon asks the source for a worker: it starts `node wrapper.cjs` with the launch credential in `FLOW_WORKER_TOKEN` (environment only, never on the command line), one wrapper per source (an alive one is never doubled), with a hidden window on Windows. The wrapper gets an ALLOW-LISTED environment, not a copy of the daemon's: only `PATH`, home and temp variables (`HOME`, `USERPROFILE`, `TEMP`, `TMP`, `APPDATA`, `LOCALAPPDATA`, `SystemRoot`, `COMSPEC`, `USERNAME`, `LANG`, `LC_*`, `TZ`), `AWS_*`, `SBX_*`, `XDG_CONFIG_HOME`, `FLOW_CONFIG_DIR`, `FLOW_SANDBOX_*`, the proxy and certificate variables (`HTTP(S)_PROXY`, `ALL_PROXY`, `NO_PROXY`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_*`) and the `FLOW_*` ones the plugin sets itself. Provider keys, the daemon's own tokens and every other variable are not passed on. What remains: the wrapper PROCESS holds `FLOW_WORKER_TOKEN` in its environment until it has read it (it removes it from its own environment right after, and `sbx` and `aws` children get an environment without any `FLOW_WORKER_*`); `AWS_*` of the daemon, if you keep keys there, reach the wrapper. If that wrapper dies after the ask returned, the next ask fails once with its exit code and the end of its stderr (the credential redacted); this is how a startup failure reaches `flow worker list` and the bound-wait message. When the source is built, `wrapper.cjs preflight` checks the options, sbx (version, signed in) and the image (best effort); the daemon wraps any failure in its generic "Cannot load worker source ..." text, the cause after "failed:" is the plugin's own message. Stopping the daemon (or removing the source) waits for the wrapper to leave, then ends it, within about 25 s.

Needs on the daemon's machine: `sbx` at the pinned version (Git Bash is NOT needed: see "Shells" below; `git.exe` still is, for pool slots), and `sbx login` done by you (the plugin never signs in). Claude steps with all their features; Codex and OpenCode steps as plain prompts (see "Codex and OpenCode steps"). Outbound HTTP(S) from the sandbox is filtered; for raw TCP, ruleless HOST destinations were observed blocked on sbx 0.51.0 (see "Raw TCP"), public destinations are unverified. On Windows the secret files are as private as your temp folder (no owner-only ACL is set, see "Limits").

The mock end-to-end test (`src/plugin/SandboxPluginE2e.test.ts`, part of `npm test`, about 30 s) starts a REAL flow daemon of this checkout in an isolated config dir, declares the BUILT plugin artifact with `--plugin sandbox.exec --plugins-dir`, and replaces sbx by the package mock (`sbxPath`, scenario `bash-canned`). It proves: the daemon builds the source and the wrapper registers with the launch credential; a run with `requires: [sandbox]` is served by that worker (execution record: source id and step output); the sbx command lines in order (`create` with `--cpus`/`-m` and exactly the two mounts, the step `exec`, then `rm --force`) with the mounts still existing at `rm` and the daemon releasing the workspace only after the removal; a second run gets a fresh sandbox from the same wrapper; no launch credential on a command line, in a recorded environment or in the daemon log; a flow without requirements is NOT routed to the sandbox worker (the source declares guarantees, so it is requirement-only): it runs on a forked host worker and the sbx mock sees no call, and a requirement-less flow and a `requires: [sandbox]` flow started together both complete; a flow with the removed `workerType` is rejected at run start with `WORKER_TYPE_REMOVED` and the migration text; a source that cannot start fails the bound step with the daemon's "Last contact with source ... failed" message. It does NOT prove any isolation (the mock runs no VM and no bash: the script step does not run, the mock prints canned output), that the real sbx accepts the flags, the image, Bedrock, the duration of a real `sbx rm`, or Windows file locks. It is not a substitute for the live check.

Residuals, stated plainly. (1) "An alive wrapper of this source" is judged by its own child handle and, after a daemon restart, by the pid in its presence file: a pid the system has reused for another process makes the plugin think the wrapper is alive and not start a new one until the file is removed (`~/.config/flow/sandbox-presence/<wrapper id>.json`, or `leftover` after the machine restarts); the file has no process start time to compare. (2) On Windows there is no polite stop signal: after waiting for the wrapper to leave by itself, `dispose` ends the whole process tree with `taskkill /T /F`, which skips the wrapper's own cleanup (its secrets directory and presence file are left; the next start sweeps stale secret directories older than 24 h, and `leftover list` shows a sandbox that stayed). On other systems the wrapper gets SIGTERM first and cleans up. (3) The values of the options are checked for shape, length (512 characters) and control characters; `image` must not start with `-`; `sbxPath` must be an existing local file.

Two environment variables exist for tests only and must not be set in production (the plugin writes a warning to stderr when `FLOW_SANDBOX_PLUGIN_WRAPPER` is set): `FLOW_SANDBOX_PLUGIN_WRAPPER` (a script that stands in for `wrapper.cjs`) and `FLOW_SANDBOX_PLUGIN_DISPOSE_MS`.

### Routing and isolation against injected steps (read this before relying on the sandbox)

A flow reaches the exec wrapper in one of two ways, and only one of them isolates.

| Routing                                                                | How it is declared                                                                                                                                                                                                                                                              | Injected steps (a model calls `provideSteps`)                                                                                         |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **Labels** (what only the prototype scripts and their live checks use) | source: `flow worker source add <id> --provider built-in:command --labels sandbox ...`; flow: steps with `labels: [sandbox]`                                                                                                                                                    | **NOT isolated.** An injected step carries no labels, so the daemon may run it on a host worker, outside the sandbox.                 |
| **Requirements** (the target)                                          | source: `flow worker source add <id> --plugin sandbox.<implementation> --plugins-dir <absolute dir> ...` (the plugin `sandbox.exec`, see "Plugin" above); flow: `requires: [sandbox]` at flow level (injected steps inherit it), or a profile such as `profile: untrusted-code` | Isolated: every step of the run, injected ones included, is offered only to sources whose declared guarantees cover its requirements. |

`workerType` is gone from the core: a flow that still has it is a validation ERROR (`WORKER_TYPE_REMOVED`) whose message carries the migration (`requires: [sandbox]` or `profile: <name>`; `flow worker source list` shows the guarantees your sources declare). A source declared with `--provider` only (the prototype scripts) declares no guarantees, so **a flow with `requires: [sandbox]` cannot use the prototype sources at all**: it is refused at run start unless a declared source guarantees `sandbox`.

**The sandbox source is requirement-only.** A source that declares a non-empty `guarantees` list (this plugin does, in the manifest and on the instance) is offered only steps whose non-empty `requires` it fully guarantees: a flow without requirements, label-only matching and the injected steps of such a flow never reach it, and the daemon never asks it for a worker on behalf of a requirement-less run. Registering the sandbox source therefore does NOT attract other flows: they keep running on host workers (their host-only steps keep working there), and its connected workers do not count against `queue.concurrency`, so they cannot stall unrelated runs. The former `exclusive: true` flag is removed from the plugin (the core still accepts it, deprecated and ignored when guarantees are declared). It is fail-closed: a source loaded from a plugins directory is requirement-only from its manifest guarantees before its instance is built.

### Requiring guarantees (`requires:`)

A flow asks for the sandbox with `requires: [sandbox]` (flow level; a step may add entries; injected steps inherit the flow's). The daemon matches each entry, by equality, against the guarantees of the AUTHENTICATED source instance, never against worker labels (a worker declares those itself), and filters in the router before any acceptance plugin. This plugin declares, in the manifest (static upper bound) and on the instance (what routing reads), the same list, kept equal to `SANDBOX_GUARANTEES` (`src/exec/RequiresGuard.ts`) by a test:

| Guarantee              | What backs it                                                                                                                                                                                                                     |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sandbox`              | every step process runs in an sbx VM (`SbxProcessLauncher`); live: `ExecLiveCheck`, `PluginLiveCheck`                                                                                                                             |
| `fs=confined`          | the VM mounts exactly the run's workspace and `.meta` (`RunMounts`); only their ancestors are visible, nothing can be created beside them (`PoolSlotLiveCheck`, one machine). The pool slot itself is writable (T-16)             |
| `env=clean`            | the host environment is not passed into the VM (`VmEnvironmentFilter`); `ExecLiveCheck` asserts no AWS key, no launch token, no ambient variable                                                                                  |
| `ports=private`        | the plugin publishes no port; a listener started in a VM was not reachable from the host (`PortsLiveCheck`, one machine, sbx 0.51.0). Limit: VMs have identical private addressing, so a VM-to-VM probe by address cannot be made |
| `fs=readonly-enforced` | the run's workspace is a `:ro` SECONDARY mount and `.meta` the read/write primary, built from the run's requirements (see "Read-only runs: `profile: inspect`"). Proven on one machine, sbx 0.51.0                                |
| `clean=run`            | a fresh VM per run, removed at the end of the run. The pool slot content (the workspace) persists                                                                                                                                 |

NOT declared, on purpose: `net=filtered` (raw TCP to public destinations is unverified and an allow-all machine policy would make it false: see "Raw TCP"; it cannot be verified without an external receiver). A flow requiring it is refused at run start (no declared source provides it).

### Codex and OpenCode steps (plain prompts)

A model step with `provider: codex` or `provider: opencode` runs in the sandbox like a Claude step, with fewer features. Supported: a prompt, the step's `model`, `skipPermissions`, `tools` restrictions the engine turns into flags, and a session id. Refused with a message that names the step, the tool and what to do: `mcpServers` and `toolHooks` on the step (an MCP server names a host program and host paths; a hook is a script the engine writes in the host temp directory). The engine's own MCP server (`provideSteps`) is NOT given to these tools: **a codex or opencode step cannot add steps**. Claude steps keep it.

|                                    | claude                                                          | codex                                                                                                                                                                         | opencode                                                                                                                                                                                                           |
| ---------------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Credentials                        | `credential_process` profile (`AWS_PROFILE`, `AWS_CONFIG_FILE`) | the same file, selected by `model_provider = "amazon-bedrock"` in a `config.toml` the wrapper writes in `CODEX_HOME` (`CodexBedrockSettings.configToml`, plugins feature off) | `AWS_PROFILE`, `AWS_REGION`, `AWS_CONFIG_FILE`                                                                                                                                                                     |
| Session store on the mount         | `CLAUDE_CONFIG_DIR`                                             | `CODEX_HOME`                                                                                                                                                                  | `XDG_DATA_HOME` (under `<meta>/sessions/<tool>`)                                                                                                                                                                   |

A tool's hosts are opened when its first step is served, not at sandbox creation. What the wrapper does not forward to the VM: the isolated `XDG_CONFIG_HOME` the engine makes for opencode in the host temp directory (`opencode-run-<uuid>`).

**Core limitation, interim workaround.** On a WINDOWS host the engine's resolvers for codex and opencode (`CodexModelProvider.findCodexCommand`, `resolveOpenCodeCommand`) branch on the host platform and ignore `launcher.isolatesEnvironment`: they look for `.cmd` files on the host and fall back to the bare name with `shell: true`. The translator therefore runs `codex` or `opencode` with arguments and `shell: true` directly in the VM, no shell (only those two names; any other name keeps the refusal). The clean fix is in the core (a resolver that asks the launcher, as `BashShellStrategy` does since 1f4b567a); reported to flow-owner. On a POSIX host `which codex` through the launcher works and the rule is not used.

Proof level: mock e2e on a real isolated daemon through the engine's own mock CLIs run inside the sbx mock (`SandboxPluginE2e`: codex's store and credentials file in the environment, opencode without the host XDG directory and without an inline config); unit tests for the refusals, the preparer, the translator and the environment filter. LIVE on real sbx 0.51.0 with real Bedrock, one short prompt each, on a Windows host (`PluginLiveCheck` with `PLUGIN_TOOLS_ONLY`): codex answered OK with `openai.gpt-5.6-terra` using the Codex profile (`PLUGIN_PROFILE=<codex profile>`; the Claude profile of this account gets `403 bedrock-mantle:CreateInference`, which shows the request reaches Bedrock with the sandbox's credentials), opencode answered OK with `amazon-bedrock/anthropic.claude-haiku-4-5-20251001-v1:0`; each session store exists on the host under `<run>.meta/sessions/<tool>`; the sandbox was removed. NOT proven: session resume (codex 0.149.1 is pinned because 0.164.0 fails `codex exec resume` with `CODEX_HOME` on the mounted directory), tool calls (a tool use inside the VM), `skipPermissions` and `tools` flags against the real CLIs, a POSIX host, two tools in one run, and the `opencode` flag probe (`--auto`) in the VM.

### Windows and POSIX hosts

The exec variant is meant to work on a Windows host and on a POSIX host (macOS, Linux; spec decision 23). The code takes the platform as a parameter and the translators use `path.win32` / `path.posix` explicitly, so both behaviours are unit-tested on any machine (tests named "on a Windows host" / "on a POSIX host").

How the translator tells a HOST path from anything else in a command line (`StepCommandTranslator`):

| Host                           | A host path is                                                                                                 | What happens to it                                                                                           |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Windows                        | any `C:\x` or `\\server\share` path (a drive letter cannot be a VM path)                                       | a generated temp file is copied into the VM; a path under the mounts is translated; anything else is refused |
| POSIX                          | an absolute path under the two mounts or under a known host directory (the temp directory, the home directory) | same three outcomes                                                                                          |
| POSIX, any other absolute path | not recognised: assumed to be a VM path and passed through (host and VM paths look alike)                      | pass-through, pinned by a test                                                                               |

**When the translator refuses a host path** the message names the value and gives the way out. For an argument that is a host file outside the mounts: `argument "<path>" looks like a host path that is not mounted in the sandbox ... If it is a file, put it under the workspace and pass that path. If it is a literal value, not a file, do not pass it as a command-line argument: write it in the script text, which is never inspected.` Both ways are accepted by the translator (tests "accepts the workaround ..."): a file under the workspace is translated, and a script's text is never read. A path that merely LOOKS rooted but lies outside the mounts and the known host directories is not refused on a POSIX host (see the table), so the refusal only concerns values under the temp or home directory or the mounts. A UNC argument, a cwd or `workingDir` outside the mounts, a host path used as a program and an MCP server that is not the engine's each name the offending value and say what to use instead (tests in `StepCommandTranslator.refusals.test.ts`, `ExecAssignment.platform.test.ts`, `McpConfigRewriter.test.ts`).

The host node is recognised wherever it lives. A `workingDir` or `flowWorkingDir` that is absolute in the host's syntax must lie inside the mounts. `sbxPath` is checked for a network path (`\\server\share` or `//server/share`) before the absolute-path check.

Proof level: platform-injected unit tests (every case for both flavours) and the Windows host runs. NOT yet shown on a real Linux or macOS machine: the CI job `unit-tests` (ubuntu) is the first real run, and `PluginLiveCheck` has only been run on Windows.

### Mounts use the resolved directories

The wrapper resolves the workspace and `.meta` paths of an assignment (links, junctions, 8.3 names) ONCE, runs the layout check on the resolved directories (`.meta` outside the workspace, pool only) and gives `sbx create` exactly those resolved paths: nothing is resolved again between the check and the mount. The engine keeps its own spelling in the execution context and in the paths it passes to the launcher; `PathTranslator` accepts both spellings and translates them to the sandbox form of the mounted directory, and paths reported back by the VM come out in the mounted (resolved) form. Limit: a real directory replaced or renamed after the resolution is not detected, which needs the same host access as editing the directory itself. Proof: unit tests with an injected resolver that answers differently the second time (`SandboxableWorkspace.test.ts`, `ExecWrapper.test.ts`) and a `PluginLiveCheck` step on real sbx with the pool reached through a junction in an ancestor directory (the core refuses a link as the pool folder itself; whether the core already resolves the slot path before the wrapper sees it was not established, so that step proves no regression with a link, not that the aliasing was needed).

### Read-only runs: `profile: inspect`

`profile: inspect` is `agent` plus `fs=readonly-enforced`. The mounts of a run follow its resolved requirements (the assign's `requires`); the capability is declared by the source, but a run without the requirement keeps the normal read/write workspace.

| Run requires `fs=readonly-enforced` | `sbx create` mounts (first = primary)                      |
| ----------------------------------- | ---------------------------------------------------------- |
| no                                  | pool slot (read/write), `.meta`                            |
| yes                                 | `.meta` (read/write primary), pool slot as `:ro` secondary |

What a step under `inspect` sees: cwd is the pool slot, readable; any write to it fails with `Read-only file system` (for the agent and for root); `.meta` stays writable (outputs, the model's session store); outputs are collected by the engine on the host as usual.

- **One mode per run.** The mounts are fixed when the sandbox is created, so every step of a run must agree: the wrapper refuses a step whose requirement differs from the run's first step (message: put it at flow level or use the profile), and refuses a mount set that does not match the requirement (never a read/write workspace under `fs=readonly-enforced`). A read-only step inside a read/write run would need a second sandbox: not implemented.
- **`host: true` is refused** on a step that requires it: a host script writes the workspace freely. (A host script also is not confined in the `fs=confined`/`env=clean` sense; the core warns for model flows, nothing else is checked.)
- **Proof level** (`PluginLiveCheck` 12/12 and `ReadOnlyLiveCheck`, sbx 0.51.0, Windows 10, one machine, 2026-11-09): a `profile: inspect` run reads the repo file, the write and the file creation in the workspace fail with `Read-only file system`, the VM shows the workspace mount as `ro`, a write to `.meta/outputs` from the VM reaches the host, the model step answers in the VM (session store under `.meta` works), and the host file is unchanged. The attack list as root (remount, bind, a second virtiofs mount, `mount(2)` from python, `/proc/<pid>/root`, a descriptor) all returned `Read-only file system` with the host file unchanged, with the read/write directory as primary and the other one `:ro`. The enforcement is host-side virtiofs. NOT proven: virtiofs protocol attacks, kernel exploits, other VM channels, other sbx versions or hosts.

Because the source is requirement-only, a step is offered to it only when its requirements are non-empty and all guaranteed; `requires: [fs=confined]` alone is enough, a step without requirements never reaches it. Write it like this:

```yaml
requires: [sandbox] # flow level: every step, injected ones included
steps:
    - id: build
      requires: [clean=run] # a step adds to the flow's list
```

An entry no declared source provides is refused when the run starts, with a "Did you mean" for a typo. `flow validate` offline cannot know the sources, so it does not catch that.

**The wrapper refuses a step the daemon did not route by a guarantee** (`RequiresGuard`, fail closed): an assignment with no `requires`, an empty one, a malformed one, or an entry this worker does not provide fails the step with a message naming what is missing and the flow syntax to add; no sandbox is created. The plugin starts its wrapper with `--require-guarantees`; the dev harness scripts (routing by labels, no guarantees) do not, and the relay harness is unchanged.

**Host-only steps FAIL in a bound run.** A strictly bound run never falls back to a host worker, so a step that cannot run in the sandbox (`cmd`, `pwsh`, a script that calls the flow daemon API, a `user_intervention` step, a Codex or OpenCode step with MCP servers or tool hooks) does not run elsewhere: it fails. Put host-only work in another flow. This supersedes the earlier plan that let such steps run on the host (design decision 27). The one exception is a script step marked `host: true` (next section).

### Model steps are confined implicitly (phase B)

A model step needs no `requires:` to land in the sandbox. When a daemon accepts a run it gives every model step the `agent` profile (`fs=confined`, `env=clean`) if at least one configured source that SERVES THE RUN'S PROJECT declares ALL of it in its static manifest list; this plugin does.

- **Depends on the machine AND the project.** The same flow is confined on a machine with this source declared for its project and runs as before otherwise. A source covers a run only if its declared entry has no `projects` option or lists the run's project id (read from the entry, never by loading the plugin). **`--option projects=a,b` is THE way to scope the sandbox source to projects, and `projects` is the only option name the core reads for this: an entry that spells it differently is read as unrestricted (serves every project).** A model step of a project that no covering source serves routes as before and prints one stderr line per step, naming the sources that serve other projects: `Warning: model step <id> runs unconfined: no worker source serving project <p> guarantees env=clean and fs=confined (<source> does, but serves other projects); declare a sandbox source for this project (flow worker source list) or write profile: agent to require it` (not with `--json` or `--quiet`; `flow validate` has no worker knowledge and says nothing). A run without a project id is covered only if no declared source restricts its projects. Decision record: `.claude/plans/2026-11-13_implicit-confinement-per-project.md`.
- **No opt-out.** While a covering source exists a model step is confined or the run is refused. A source that covers only part (for example `fs=confined` without `env=clean`) does not count.
- **Workspace.** The source accepts only `workspace: pool`: a model step with another workspace is refused at run start (`WORKSPACE_KIND_NOT_ACCEPTED`, naming `pool`), never run unconfined.
- **Record.** `flow show <id> --json` has `requirements.steps` (what is enforced) and `requirements.implicit` (`requires` and `steps` the daemon added). A resume uses the record, not the machine.
- **Scripts are unchanged.** A script step without requirements never reaches the sandbox source, so a flow mixing both keeps its scripts on host workers unless it writes `requires` (or `host: true` for a script that must run on the worker machine).
- Proof: `SandboxPluginE2e` (real isolated daemon, sbx mock) for the four cases above plus the partial-coverage source, and `PluginLiveCheck` on real sbx.

What `flow worker source list` prints for this source (captured from the e2e daemon):

```text
sandbox-agent	sandbox	max=1	labels=(none)	plugin=sandbox.exec	guarantees=clean=run, env=clean, fs=confined, fs=readonly-enforced, ports=private, sandbox	workspaces=pool	requirement-only

Declared sources describe intent. Use "flow worker list" to see live workers.
guarantees= is what the plugin manifest declares the source can enforce (a step requires it with requires: or profile:); workspaces= the workspace kinds it accepts.
requirement-only: a step is routed to it only when it requires something it guarantees, and its workers do not count against queue.concurrency.
```

### Host scripts (`host: true`)

```yaml
steps:
    - id: sync
      type: script
      host: true # runs on the machine of the sandbox worker, not in the VM
      script: git fetch
```

- Script steps only; the daemon refuses it elsewhere, and the wrapper refuses a `host: true` model step too. Absent or `host: false` = the VM, as before. Injected steps can never carry it.
- Served by the wrapper itself, never handed to another worker. The `requires:` guard still applies (the step carries the run's requirements), and no sandbox is created or woken for it.
- cwd is the run's workspace (the pool slot). Timeout, cancel, kill-tree and output capture are the engine's, identical to a VM step; the log has one line `script step "<id>" runs on the host (host: true)`.
- **Environment is an allow-list** (`HostScriptEnvironment`): `PATH`, system and temp directories, home directories, locale, `FLOW_BASH_PATH`, plus the names the step declares in `env` / `secrets`. Everything else of the wrapper's environment is withheld, always including `FLOW_WORKER_*`, `FLOW_SANDBOX_HOST_*` and `AWS_*` unless the step declares the name itself. The log names the withheld variables (never values).
- **Security statement.** A host script runs with YOUR rights, on files an agent may have written in the slot (hooks, `.git/config`, package scripts). `flow validate` and `flow run` warn `HOST_SCRIPT_WITH_MODEL_STEPS` when the flow also has a model step: remove `host: true`, or keep it only for a script that reads nothing a model wrote. The environment filter does not make that safe; it only keeps the wrapper's secrets out.
- The relay harness (dev only) refuses `host: true`: it cannot serve it. It forwards `requires` to the inner worker.
- Live proof: `PluginLiveCheck` runs a `host: true` script next to a VM script in one run (different hostname and user, a canary variable of the wrapper environment absent, cwd = the pool slot).

The wrapper cannot see the flow, so it never claims isolation. At startup it reads the registry of worker sources it can see (`worker-sources.json`, the file `flow worker source list` prints; same user and `XDG_CONFIG_HOME` only) and logs one line: an info line saying the source declares guarantees (steps arrive only with `requires`) when it has a plugin ref, otherwise ONE `ISOLATION WARNING` (no plugin ref, source not found in that registry, or registry unreadable) saying label routing is not isolating. It does not read the daemon's own state, so a daemon with another config directory shows up as "could not be verified".

Network, in user-facing words: outbound HTTP(S) from the sandbox is filtered (machine policy plus per-sandbox allow rules; about 195 entries on the balanced preset). Raw TCP to ruleless host ports was observed blocked on sbx 0.51.0; raw TCP to public addresses is unverified. Never describe the sandbox as "network isolated".

### Run end (`run_end`, class `ExecRunEnd`)

The exec wrapper declares the `run-events` feature in every `ready` (the constant of flow-cli `Protocol.ts`; the relay harness does not). The daemon then sends `run_end { executionId, reason }` once per run to a worker that was handed a step of it, and releases the run's workspace when the worker answers `run_end_ack` or its wait expires (`worker.ackTimeoutSeconds`, 30 s by default, 120 s at most). The ack is therefore sent only AFTER the sandbox that mounts the workspace is gone.

| reason                                                                         | what the wrapper does                                                                                                                                                                                                    | ack                                                                                           |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| `completed`, `failed`                                                          | `SandboxLifecycle.endRun`: the sandbox is REMOVED (serialized on the lifecycle queue). The prepared credentials and mounts of the run are forgotten. The wrapper stays registered and the next run gets a fresh sandbox. | after the removal                                                                             |
| `daemon_stopping`                                                              | the sandbox is stopped and KEPT (the run may resume; `leftover list` / `leftover remove`)                                                                                                                                | after the stop                                                                                |
| a run it holds no sandbox for                                                  | nothing to remove (its create may have failed): the daemon counts this worker as served and waits for it                                                                                                                 | at once                                                                                       |
| second `run_end` of the same run (the daemon sends it once and never re-sends) | nothing is removed again (`endRun` is idempotent); defensive, not a retry mechanism                                                                                                                                      | again; harmless: an ack the daemon no longer waits for is only warned about and dropped there |
| unknown reason / no run id                                                     | logged and ignored: protocol drift must be visible                                                                                                                                                                       | none                                                                                          |

A removal that fails (anything but "not found") is retried once after 2 s by the WRAPPER; the daemon sends `run_end` once per run and does not retry it. If the retry fails too, NO ack is sent: the daemon waits its bound, releases the workspace, logs that this worker did not acknowledge, and the sandbox stays until `leftover remove`. The wrapper's log says, with the cause: `sandbox <name> could not be removed: <cause>. No run_end_ack was sent ... Finish by hand: leftover remove <name>`. A step of the run that is still running (a sibling after a terminal failure; the daemon waits for it to settle first, bounded) does not delay the removal: `sbx rm --force` ends its processes and the daemon drops whatever it reports after `run_end`. `sbx rm` duration is not measured yet (live check pending): if it exceeds the daemon's bound, raise `worker.ackTimeoutSeconds`.

Mapping limits:

- Kill: the process is unreachable from the host, so `kill`/`killTree`/`killTreeAndWait` STOP THE SANDBOX (lifecycle `stopAfterStepTimeout`), then abort the host `exec`. SIGTERM is as hard as SIGKILL (no grace, no traps); the exit-time kill of the engine cannot wait for the stop. Staged files stay if the VM is stopped.
- Exit: only a numeric code is reported; a signal death in the VM is 128+n, `signalCode` is set only for processes the launcher ended. `snapshotDescendants` returns `[]` (the stop kills the tree); `signalProcesses` with pids throws.
- stdin: taken once at start (write + `end()` right after `spawn`); `stdio: 'inherit'` throws; `detached` ignored; `shell: true` command lines run under `/bin/sh -c`.
- Windows paths in script text or env values are warned about, not translated (rendered `${{ context.workspaceDir }}` is a host path).
- Codex and OpenCode run as plain prompts only (next section); a step with MCP servers or tool hooks is refused. Interactive steps and `user_intervention` are refused.
- MCP: the engine's callback server listens on host `127.0.0.1:<random>`. The VM runs `image/mcp-callback-forwarder.cjs` (listens on VM loopback, relays to `host.docker.internal:<port>`, then loads the unmodified `mcp-server.cjs`). The tool answers "Successfully injected" when its local write succeeds, not when the host received it (fire and forget, also without sandbox): a missing rule gives a false positive.

### Findings (reported, not fixed in core)

- **Shells (core 1f4b567a, `SbxProcessLauncher.isolatesEnvironment = true`).** The engine's bash and pwsh strategies resolve the shell ONLY through the launcher: `which bash` is answered from the table primed in the VM (`/usr/bin/bash`), `which pwsh` fails with "not installed in sandbox ... shell: pwsh cannot run" (PowerShell is not in the image). No `FLOW_BASH_PATH`, no Git locations, no PATH scan on the host. A script step also gets an allow-list plus what it declares instead of the whole worker environment (`VmEnvironmentFilter` stays as the second layer). `StepCommandTranslator` no longer maps a host `bash.exe`: it refuses one (an old flow-cli) with the fix. Proved on this Windows host with Git's bash and sh directories removed from the PATH of the daemon and the wrapper only (`PLUGIN_HIDE_GIT_BASH=1 scripts/live/PluginLiveCheck.mjs`, 7/7: the script ran with `/usr/bin/bash` in the VM). Still true: `shell: cmd` is unsupported under a sandbox launcher; the wrapper declares `shellCapabilities: ['bash']` statically (it does not probe the host); the generated script file is written in the host temp folder and copied into the VM by `VmFileStager` (verified by that run); the host still needs `git.exe` for pool slots (not Git Bash); the repository tests `CredentialProcessScript` and `CredentialGlueInstaller` run real bash scripts and need `bash` on the PATH of the machine that runs them.
- Injected steps carry no labels (plan H4), so under LABEL routing (the prototype scripts) an injected step may run outside the sandbox. Under requirement routing (`requires: [sandbox]` at flow level, the plugin) an injected step inherits the run's requirements and stays in the sandbox. The MCP surface does not make "the sandbox cannot add steps" true: a Claude step can add steps (they run in the sandbox under `requires`), a Codex or OpenCode step cannot.
- Raw TCP from the VM to a host port without a rule is blocked, with the rule it passes: see "Raw TCP" above (the M4 observation to the contrary is superseded).

## Image

`image/Dockerfile` (tag `flow-sandbox:m2`, `m7` adds `/opt/flow/mcp-callback-forwarder.cjs`, `flow-sandbox:m4` adds the flow worker files, see M4): base `docker/sandbox-templates:claude-code-docker` pinned by digest, `@openai/codex@0.149.1`, `opencode-ai@1.19.4` (claude 2.1.306 and node 22 come from the base), npm cache cleaned, placeholder files in `/opt/flow` copied with `COPY --chmod=0644` (the flag also applies to the directory, so it is reset to 0755 right after; otherwise `agent` cannot list it).

Codex is pinned to 0.149.1 because 0.164.0 fails `codex exec resume` with `CODEX_HOME` on the mounted dir (`list_turns is not supported yet`). Not isolated whether that is a version regression or mount behaviour; re-test when bumping codex.

Rebuild (host `docker build` is not assumed): `node --import tsx packages/flow-sandbox/image/build-image.mjs [--tag flow-sandbox:m2]`. It creates a builder sandbox (Docker Hub and npm must be reachable), runs `docker build` and `docker save` inside, runs `sbx template load`, then removes the builder and the ~1.3 GB tar. About 3 minutes. Use the image with `image: 'flow-sandbox:m2', pull: 'never'`. Older tags (`m0b`, `poc-m0`) stay in `sbx template ls` until removed with `sbx template rm`.
